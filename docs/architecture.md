# Architecture

REGENT is an npm workspaces monorepo with one engine package and three applications:

```
packages/core   @regent/core   verification engine (pure TypeScript, no I/O)
apps/api        @regent/api    HTTP API, storage, auth, reports; serves the console in production
apps/cli        @regent/cli    offline command line over the same engine
apps/web        @regent/web    React console (visualization only)
```

Node 24 runs the TypeScript sources of the engine, the API and the CLI directly through its built-in type stripping, so there is no server compile step. Only the web console is bundled (Vite).

## Pipeline

| Stage | What happens | Module |
|---|---|---|
| Ingestion | Parse JSON (bundle, array, single record) or JSONL; never evaluate input. API: size limits, rate limits, `POST /api/events`. CLI: file read, 50 MB limit. | `normalize.ts` (`parseEvidenceText`, `flattenInput`); `apps/api/src/app.ts`; `apps/cli/src/main.ts` |
| Normalization | Strip control and bidi characters from every string (`text.ts`); null malformed references; validate each record against zod schemas, reject with a reason or accept; apply legacy aliases; canonicalize scopes and timestamps; collapse or flag duplicates; apply revocation records; sort deterministically. | `schemas.ts`, `normalize.ts` (`normalizeRecords`) |
| Identity resolution | Index principals, execution identities, credentials, tools, resources and policy versions; any reference to an unregistered entry becomes an unknown reference. | `chain.ts` (`buildIndex`), `verify.ts` |
| Chain reconstruction | Locate the actor's delegation (explicit, direct, or unique lookup) and walk parents back to a root principal; record breaks. | `chain.ts` (`resolveActorDelegation`, `ChainAnalyzer`) |
| Scope resolution | Compute available, effective, amplified, inherited and policy-restricted scope per hop with the scope algebra; upper bounds when upstream is unknown. | `scope.ts`, `chain.ts` |
| Policy evaluation | Apply the scope ceiling and approval requirements of the recorded authorization policy version; check policy traceability. | `verify.ts` |
| Invariant verification | Ten dimension checks per action, temporal validity at action time, derived authorization decision. | `verify.ts` |
| Finding generation | Emit findings under the active rule set with deterministic ids, evidence references and record digests; summary. | `verify.ts`, `rules.ts`, `digest.ts` |
| Visualization | Explanation and replay generated by the engine; the console renders chains, hops, replays and findings returned by the API. | `explain.ts`, `replay.ts`; `apps/web/src` |
| Reporting | `regent.finding/v1` JSON, CSV, evidence package, PDF reports, control evaluation. | `export.ts`, `grc.ts`; `apps/api/src/services/pdf.ts` |

`analyze(input)` in `analyze.ts` runs ingestion, normalization and verification in one call. `investigate.ts`, `timetravel.ts` and `diff.ts` are further views over a finished run.

## Three structures

The data model (`packages/core/src/types.ts`) keeps three structures apart. See [concepts.md](concepts.md#three-structures-kept-apart) for why.

- **Delegation chain** — `Delegation` records, linked by `parent_delegation_id`, resolved into `ReconstructedChain.hops` (`ResolvedHop[]`). Only principals appear in it.
- **Execution path** — the `Action` record's actor, tool, execution identity, credential, resource and policy version, resolved into `ActionVerification.execution_edges` (`INVOKES`, `EXECUTES_AS`, `AUTHENTICATES_WITH`, `TARGETS`, `GOVERNED_BY`).
- **Evidence chain** — `Finding.evidence` (`EvidenceRef[]`), each a pointer to a normalized record with its SHA-256 digest.

The separation is enforced by types, not convention: `ResolvedHop` has delegator and delegatee principal ids and nothing else; `ExecutionIdentity` has a `bound_principal_id` but is never a hop; a `Credential` has a binding to an execution identity and no principal field at all. An execution identity's `provisioned_scope` (standing permissions) is a separate field from any delegated scope and is never merged into effective scope.

In PostgreSQL the same separation holds: `principals`, `delegations`, `actions`, `execution_identities`, `credentials`, `tools`, `resources` and `authz_policies` are separate tables. They deliberately have no foreign keys between them, because imported evidence is untrusted and a dangling reference is a finding to report, not a row to reject. Foreign keys are used only for REGENT's own data (organizations, users, datasets, runs).

## Package boundaries

| Package | May | May not |
|---|---|---|
| `@regent/core` | Pure computation over its inputs; `zod` for schemas; `node:crypto` for SHA-256. | Read the clock (`Date.now`), use randomness (`Math.random`), make network requests (`fetch`), touch the DOM (`window`, `document`). Enforced by ESLint rules on `packages/core/src/**`. |
| `@regent/api` | Storage, authentication, authorization, rate limiting, logging, PDF rendering. Calls the engine for every verdict. | Compute verdicts itself. |
| `@regent/cli` | Read files, write `.regent/last.json` and exports, call the engine. | Talk to the API (it is offline). |
| `@regent/web` | Render what the API returns; import engine **types** with `import type`. | Import engine functions. ESLint forbids value imports of `@regent/core` in `apps/web/src/**` (`@typescript-eslint/no-restricted-imports` with `allowTypeImports`). |

The console never decides whether something is allowed. Anything role-dependent in the UI is presentation only; the API enforces every permission. A verdict on screen is always one the API computed.

## API process

`apps/api/src/index.ts` loads configuration from the environment (`config.ts`), opens the database (`db/driver.ts`), applies migrations (`db/migrate.ts`), seeds the demo organization and personas (`bootstrap.ts`), builds the Hono app (`app.ts`) and listens. Middleware order for `/api/*`: request context and structured logging, security headers, CORS, rate limit, body size limit, authentication, CSRF. Route handlers go through `WorkspaceService` (`services/workspace.ts`), which scopes every query by organization and runs verification through `@regent/core`.

A verification run stores the run summary, one row per action with the full `ActionVerification` as JSON, and one row per finding with the full finding as JSON. Reads use the latest run of the active dataset, cached in memory per dataset and run id (up to 24 entries). For each cached run the API builds one index (`indexOf` in `services/views.ts`, held in a `WeakMap` keyed by the run) mapping actions, verifications, findings, hops, delegations and credentials to each other, so views do lookups instead of scanning the whole run per item, and long lists in detail views are capped with exact totals. Triage state lives in a separate table keyed by finding id, so it survives re-runs.

Verification itself runs on the API's event loop, not in a worker thread. It is bounded by the import limits and by the timings in [testing.md](testing.md#performance).

In production (`--production` or `NODE_ENV=production`) the same process serves the built console from `apps/web/dist`, resolving paths inside that directory only and falling back to `index.html`.

## Why Hono and Vite instead of Next.js

- **The console is an authenticated single-page application behind a separate API.** It has no public pages that need server rendering for search engines, and every data view requires a session. A plain SPA served as static files under a strict CSP (`script-src 'self'`, no inline scripts) is simpler to secure than a server-rendering framework.
- **The engine must not live in UI code.** Keeping the API a separate process with its own routes makes the boundary physical: verdicts are computed in `@regent/core` behind `/api`, and the console can only display them. A framework that blends server and client components makes it easy for verification logic to drift into the UI bundle. ESLint enforces the boundary in addition.
- **One origin in production, two processes in development.** In development Vite serves the console on port 5173 and proxies `/api` to the API on port 8787, so the browser sees one origin and the `SameSite=Strict` session cookie works. In production the API serves `dist/` itself.
- **Small runtime surface.** Hono plus `@hono/node-server` is a few dependencies; the API runs as TypeScript under Node 24 with no build step.

## Why PGlite locally

The API speaks to PostgreSQL through one small interface (`Db` in `db/driver.ts`) with two implementations:

- **PGlite**: real PostgreSQL compiled to WebAssembly, running in-process. Used for local development (data in `.data/pglite` at the repository root, shared by every entry point) and for the API tests (in memory, `REGENT_DB=memory`). Nothing needs Docker or a database server to run.
- **node-postgres**: a PostgreSQL server reached through `DATABASE_URL`. Used in production and in the Docker Compose stack.

Both run the same SQL files from `database/migrations/`, and all SQL is parameterized. Each migration's SHA-256 is recorded in `schema_migrations`; an edited, already-applied migration stops startup rather than silently diverging. PGlite is single-process and in-process, so it is not a production database for REGENT; the PostgreSQL path is the production path. The production driver is tested by connecting `node-postgres` over the wire protocol to PGlite served on a local socket; the CI `postgres` job runs migrations and the API smoke checks against a real PostgreSQL 17 server (see [testing.md](testing.md)).

## Determinism

The same evidence and rule set must always produce the same result, on any machine, in any record order. Design decisions that make that true:

- **No clock, no randomness, no I/O in the engine.** Enforced by lint. Times come only from the evidence; prose times are formatted from recorded values.
- **Canonical ordering everywhere.** Strings are compared by code point (`compareStrings`), never with locale-dependent comparison. Scopes are sorted and de-duplicated; normalized records are sorted by id (actions by timestamp, then id); findings by severity, type and id; evidence references by kind and id.
- **Canonical JSON.** `canonicalJson` sorts object keys by code point and drops `undefined`, so equal content always serializes identically.
- **Deterministic finding ids.** `REG-<CODE>-<10 hex of sha256(type|rule|subject)>`. The same subject under the same rule always gets the same id.
- **Input digest.** `run.input_digest` is the SHA-256 of the canonical JSON of the normalized bundle, the rule set, the completeness schema and the engine version. Identical input, identical digest; any change to evidence or configuration changes it.
- **Caches do not change results.** Permission parsing is memoized, hops are cached per delegation, link and validity at the action time, and finding relations are collected in sets and sorted once at the end. These keep the work near-linear on large inputs; the determinism tests run with them in place.
- **Order independence.** Chain reconstruction memoizes per delegation and applies the hop limit to path length, so the result does not depend on which delegation is analyzed first. Revocations apply the earliest time regardless of order.

Tests check this directly: two runs over the demo records are byte-identical under canonical JSON; three seeded shuffles of the input records produce the same input digest and the same canonical run; finding ids are stable and match `^REG-[A-Z]+-[0-9a-f]{10}$`; and the API test re-imports the demo records and requires the stored-then-reloaded run to have the same input digest and finding ids as the engine run directly.

One input-order dependency is deliberate: when two records share an id but differ in content, the first one is kept and the conflict is reported as an ingestion error. The input is then inconsistent, and REGENT says so rather than resolving it silently.
